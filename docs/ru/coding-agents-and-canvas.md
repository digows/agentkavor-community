# Как CodingAgents видят и строят Canvas

Canvas — не только картинка для вас. Для CodingAgent это живой контекст, карта capabilities и, когда вы разрешаете,
поверхность, которую агент может организовать.

Это две разные возможности:

1. **понимать достижимый граф**, чтобы работать с Nodes, ресурсами и другими CodingAgents;
2. **редактировать структуру Canvas** через немедленные атомарные изменения.

Видеть положение Node не значит читать его содержимое, а работать с ресурсом не значит уметь удалить всё в Workspace.

## Граф — это общий контекст

При каждом новом взаимодействии Kavor передаёт CodingAgent текущее состояние его достижимой компоненты: Nodes,
Connections, Guardrails и факты, необходимые для понимания работы.

Агент может работать с любым Node, связанным путём валидных Connections, на любом расстоянии:

```text
Specification — Builder — Reviewer — Sticky Note
```

Builder достигает Sticky Note через Reviewer; Reviewer достигает Specification через Builder. Оба CodingAgents могут
обмениваться сообщениями без прямого соединения каждого ресурса с каждым агентом.

Canvas остаётся читаемым, а топология — явной: удаление Connection может разделить компоненту и изменить достижимость
при следующем взаимодействии.

## Что приходит сразу, а что читается по запросу

Kavor предпочитает полезный контекст, а не постоянный dump Workspace.

- небольшая текстовая информация может прийти вместе с состоянием графа;
- Specifications показывают lifecycle, путь и недавние outputs, а canonical Markdown остаётся в Workspace;
- Terminals показывают состояние и foreground-команду, output читается при необходимости;
- Files показывают canonical source, содержимое остаётся в filesystem;
- CodingAgents показывают состояние и рабочие факты, старые сообщения читаются по необходимости.

Большое или изменяющееся содержимое не копируется постоянно в context window. Чёткая ссылка сохраняет место для
рассуждений и настоящие источники данных.

## Сообщения тоже следуют графу

Любой достижимый CodingAgent может написать другому в компоненте; прямая Connection не нужна. Сообщения долговечны и
видны в `Messages`. Используйте их для передачи реализации Reviewer, уточнений у автора Specification, разделения
независимых исследований или возврата findings с запросом повторной проверки.

Долговечное решение не должно жить только в сообщении. Контракты сохраняйте в Specification, рабочую память — в
Sticky Note, результаты — в подходящих outputs.

## Guardrails остаются на прямой паре

Reachability задаёт доступ, Guardrail — ограничение. Если прямая Connection CodingAgent + Specification содержит
`specification_read_only`, ограничение действует на эту пару даже при другом пути. Ограничение другого CodingAgent
не становится глобальной политикой ресурса.

Визуальная близость, labels и ссылки в сообщениях не дают доступ: нужен реальный путь Connections.

## Агент видит layout, но с меньшими полномочиями

Для организации Workspace CodingAgent может видеть labels, типы и геометрию всех Nodes на Canvas. Эта layout-view не
включает configuration, content или Connections вне его графа.

Поэтому он может выровнять или переместить внешний Node, не получая доступ к содержимому. Layout — Workspace-wide;
контекст и структурные изменения — нет.

## Allow workspace editing

В advanced settings каждого CodingAgent есть `Allow workspace editing`. Опция управляет структурными изменениями,
инициированными агентом, и действует сразу без перезапуска сессии.

Когда она включена, агент в своей области может:

- создавать активные Nodes: CodingAgent, Specification, Sticky Note, Terminal, File и Schedule;
- создавать canonical Specification и materialize её на Canvas;
- добавлять поддерживаемые Connections и менять параметры Terminal Connection;
- удалять Connections;
- переименовывать достижимые Nodes и Specifications;
- настраивать достижимый Schedule;
- перемещать, изменять размер и раскрывать Nodes.

Когда опция выключена, структурные изменения отклоняются; агент должен сообщить об этом и не настаивать. Layout
остаётся доступным, потому что перемещение Node не расширяет права и не меняет содержимое.

## Структура следует графу, а не всему Workspace

CodingAgent может структурно изменять Nodes и Connections своей достижимой компоненты, а также Nodes, созданные ранее
в том же атомарном изменении. Он может создать и сразу соединить Node, не оставляя мусор, или создать ресурсы и
присоединить себя в одном batch.

Первую связь с существующим Node вне графа создаёте вы. Layout visibility не позволяет агенту присоединиться к
ресурсу, который вы никогда не делали достижимым.

## Изменения атомарны

Kavor проверяет полный набор и применяет изменения по порядку как единое целое. Если шаг не удался, предыдущие
структурные изменения batch не остаются.

Создание Terminal и Connection даёт оба результата или ни одного; orphan Node не остаётся. Возвращённый результат
содержит фактически сохранённую форму — агент должен прочитать её, а не предполагать defaults, геометрию или пути.

## Что остаётся за человеком

`Allow workspace editing` не даёт безграничный контроль. CodingAgent не может:

- удалять Nodes;
- создавать, удалять или ослаблять Guardrails;
- произвольно перенастраивать другие виды Node;
- менять человеческий контроль, удерживающий входящие сообщения на согласование;
- использовать ссылку или позицию Canvas для расширения собственного графа.

Агент может удалить достижимую Connection, поэтому запрос должен быть явным, если действие способно убрать контекст
или прервать другого CodingAgent. Kavor требует касаться Connections peers только по вашему запросу или когда это
нужно для уже делегированной работы.

## Docs MCP помогает агенту обучать Kavor

CodingAgents могут читать официальную документацию через локальный Docs MCP. Можно попросить помощь, не запоминая
имена Nodes, поддерживаемые комбинации и детали Schedule.

Документация направляет, но не даёт полномочий. Docs MCP не создаёт Connections, не отключает Guardrails и не
превращает совет в изменение Canvas.

## Три prompt для совместной работы

### Сначала объяснить

> Прочитай официальную документацию Kavor и текущий граф. Объясни минимальную структуру для задачи, какие Nodes будут
> достижимы и какие ограничения сохранятся. Пока не меняй Canvas.

### Построить проверяемый цикл

> Построй небольшой цикл со Specification, Builder, Reviewer и Sticky Note. Используй минимум Connections, создай и
> соедини Nodes одним атомарным изменением и остановись до реализации, чтобы я проверил Canvas.

### Организовать без расширения доступа

> Организуй Canvas так, чтобы намерение, реализация, ревью и доказательства читались ясно. Не создавай и не удаляй
> Connections, не меняй Guardrails и не предполагай доступ к Nodes вне своего графа.

## Checklist перед разрешением изменений

- агент объяснил ожидаемый структурный результат?
- у каждого нового Node есть конкретная функция?
- Node будет соединён в том же batch или намеренно предназначен только человеку?
- изменение остаётся в достижимой компоненте?
- удаление Connection может разделить граф или прервать другого агента?
- нужен ли прямой Guardrail до передачи ресурса?
- понятно ли, где агент должен остановиться для проверки?

Используйте CodingAgent как партнёра Canvas, а не невидимого владельца. Ценность — в возможности видеть полученную
структуру, её изменения и пределы, оставшиеся под вашим контролем.
